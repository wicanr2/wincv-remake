# WinCV Remake

[繁體中文](README.md) ｜ [English](README_en.md) ｜ **日本語**

WinCV(CView for Windows)は台湾のシェアウェアで、作者の Lcc Wizard(林健総)が
1999 年から 2011 年まで一人で保守してきました。サイトは cview.com.tw、
最終版 0.52 の更新日は 2011 年 11 月 24 日です。実行ファイル自体には
アプリケーションロジックが入っておらず、本体は同梱された Forth image です。
この repo はその image をリバースエンジニアリングし、Go で Windows に
縛られないプログラムとして書き直しました。目標は「だいたい同じ機能なら
よい」ではありません。原版の画面のどのマスに何の文字が置かれ、そのマスが
何色かまで、原版を実測して書き起こしており、8×16 のマスは 1 ピクセルも
ずれていません。

## 何を達成したか

2004 年 8 月、あるブログに「DOS 時代に一番好きだったソフト」として CView が
取り上げられ、画像を見るのが「とても速い」と書かれていました。その記事の
最後の一文は「Linux 版を作ってくれたら本当に嬉しいのに~~」でした。

原版は 2011 年 11 月 24 日で止まっています。32 ビットの Windows 実行ファイルで、
解凍と画像表示は一群の Windows DLL——`unrar.dll`、`unlha32.dll`、`CAB32.DLL`、
`FreeImage.dll`——に依存していました。これらの依存関係は 1 つのプラットフォームに
縛られており、次の版の Windows でも読み込める保証はどこにもありません。

実行ファイルを残すことは、このソフトを残すことにはなりません。残すべきなのは
挙動です。ソート規則、フィールドの揃え方、エンコーディングの判定方法、
どのキーを押すと何が起きるか——これらは作り直して初めて残ります。

そのため、リバースエンジニアリングの対象は 52 KB の `wincv.exe`(こちらは
Forth kernel に過ぎず、アプリケーションロジックを持ちません)ではなく、
1.52 MB の `WINCV.IMG` でした。3663 個の word、9497 件のシンボル、29 個の
named color の RGB 値を、それぞれ word body から 1 つずつ取り出しています。
ファイル一覧の各列の色は、両方のスクリーンショットを同じグリッドで切り分け、
マスごとに実測した結果です——インジケーター列は濃い青一色でカーソルが
通っても変わらず、日付は緑固定、ロングファイル名の列には下線が付きます。
ターミナルの慣習で推測しても、1 つも当たりません。

12 種類のアーカイブ形式をすべてサポートしており、うち LZH、`.Z`、CAB、ARJ、
ARC、ACE の 6 種類は自前で実装しました。いずれも参照実装と照らし合わせて
1 ファイルずつ sha256 で検証しています——p7zip(675 メンバー)、ncompress、
cabextract、arj 3.10、arc 5.21、acefile(269 メンバー)です。比較対象(oracle)が
ない形式についてはデコーダを書きません。検証していないデコーダは、内容が
あるように見えて実際は誤ったファイルを黙って出力してしまうからです。

原版が読めなかったものも接続しました。gopher サイト、ウェブページ、
EPUB 電子書籍、Word、PowerPoint、Excel、PDF——すべて同じ画面と同じキー操作で
扱えます。やり方は、それらを「段落ごとのテキスト、1 つずつのリンク、
数枚の画像」に一律圧縮することです。これはちょうどこの文字セルグリッドで
描画できるものであり、また 1999 年当時のこのインターフェースがもともと
やっていたことでもあります。PDF にはもう 1 つの見方があります。`V` で
ページ全体を実際に描画し、パス、塗り、グラデーション、透明度、埋め込み
フォントのグリフ輪郭まで自分で解釈し、poppler の描画結果と照らし合わせて
マスごとに測定しています。

現在は Linux、Windows、macOS、Android 上で動きます。2004 年のあの
「Linux 版を作ってくれたら」という一文に、22 年を経てようやく応えることが
できました。

これを台湾ソフトウェアのルネサンスと呼ぶのは大げさです——これはただの
1 本のソフトに過ぎません。ですが当時は多くの人が毎日使っていたものであり、
32 ビット Windows をインストールできる環境がなくなる時代に消えていくはず
でした。今はもう、そうはなりません。

## CView とは

CView は DOS 時代のファイルブラウザで、F-PC Forth で書かれていました。
Windows の時代に入ってから、作者は Win32Forth v4 の subroutine-threaded
code で書き直し、WinCV となりました。両方のバージョンの使用感は同じです。
画面いっぱいの文字セルグリッドの中でカーソルがファイル一覧を移動し、
1 回押すとテキストファイルが開き、もう 1 回押すとアーカイブの中に
入っていきます。どこかの一時ディレクトリに展開する必要はありません。

当時使っていた人の多くが記憶しているのは速度です。2004 年、Tsung 氏は
自身のブログで CView を「DOS 時代に一番好きだったソフト」と書き、画像を
見るのが「とても速い」と述べています。記事の最後の一文は「Linux 版を
作ってくれたら本当に嬉しいのに~~」でした
([Tsung's Blog, 2004-08](https://blog.longwin.com.tw/2004/08/cview/))。

代替ソフトを何年もかけて探した人もいます。大丙氏は 2006 年から 2009 年に
かけて、WinCV 0.5、FreeCommander、Universal Viewer 5.1.0、
Directory Opus 9.5 を順に試しましたが、多くは中国語の折り返しや
エンコーディングでつまずきました。求めていたのは「DOS 時代の CVIEW の
ようにテキストファイルを素早く見られるソフト」で、途中「残念ながら
ACDSee はテキストを見られない」ともこぼしています。最終的な結論は
Directory Opus がかろうじて使えるというものでした
([大丙の記事](https://blog.dabinn.net/cview替代軟體/))。

作者側の記録も残っています。2012 年 1 月、作者のブログのコメント欄に
「あなたの wincv は本当に素晴らしい……毎日使っています」という書き込みが
あり、作者は自分の時間が限られていて更新が遅いと返信しています
([lcc-wizard.blogspot.com](http://lcc-wizard.blogspot.com/2012/01/blog-post.html))。
軟體王の [WinCV 0.52 ダウンロードページ](https://www.softking.com.tw/7555/)
は今日でも公開されており、繁体字中国語のファイル管理ツールの分類に
載っています。ファイルサイズは 5.56 MB です。

![テキストビュー](docs/ui/shot-viewer.png)

*リメイク版が原版自身の `whatsnew.txt` を表示している様子。Big5 エンコー
ディングの判定、シンタックスハイライト、Big5 全角文字が確認できます。
1 行目の横帯がカーソル(カーソルバー)で、`↑↓` で移動します。*

## なぜ書き直すのか

原版は 32 ビットの Windows 実行ファイルで、解凍と画像表示は一群の
Windows DLL に依存していました。`unrar.dll`、`unlha32.dll`、
`unarj32j.dll`、`unacev2.dll`、`CAB32.DLL`、`7-zip32.dll`、そして
`FreeImage.dll` と Intel の `ijl15.dll` です。これらの依存関係は
1 つのプラットフォームに縛られており、次の版の Windows でも読み込める
保証はありません。

残すべきなのは挙動です——ソート規則、フィールドの揃え方、エンコーディングの
判定方法、どのキーを押すと何が起きるか。これらは作り直して初めて残ります。
そのためリバースエンジニアリングの対象は `wincv.exe`(こちらはわずか
52 KB の Forth kernel で、アプリケーションロジックを持ちません)ではなく、
プログラム本体が入っている 1.52 MB の `WINCV.IMG` でした。

2004 年のあの「Linux 版を作ってくれたら」という一文は、原作者からの
応答を待てないままでした。この repo は自分の手で作った版です。

## 原版との違い

| 項目 | 原版 WinCV 0.52 | 本リメイク版 | 説明 |
|---|---|---|---|
| プラットフォーム | 32 ビット Windows | Linux / Windows / macOS / Android | 同じ `internal/` を 4 プラットフォーム分ビルド |
| 解凍 | 外部 Windows DLL | 純粋な Go:標準ライブラリ、サードパーティパッケージに加えて自前実装のデコーダ 6 種 | 12 種類の形式すべてに対応 |
| 画像デコード | `FreeImage.dll` + Intel `ijl15.dll` | 純粋な Go によるデコード | 12 種類中 11 種類に対応、Photo CD のみ未対応 |
| 半角フォント | 付属のビットマップフォント `cvga.fon`、8×15 | 原版の `.FON` を直接解析してグリフを取得 | グリフの正解データはフォントファイル自体から得ています |
| 全角中国語字形 | Windows GDI がシステムフォントで描画(image 内では「新細明體(PMingLiU)」を指定) | 倚天(ETEN)ビットマップ字庫 `STDFONT.15`、16×15 | 原版の中国語の見た目は各ユーザーの Windows 環境によって変わるため、リメイク版には確定的な供給元が必要でした |
| マスのサイズ | 8 × 16 | 8 × 16 | グリフ 8×15 は上揃えで、下に 1 行分の余白が残ります。原版の行高は、同時に要求される 16 px の全角フォントから来ています |
| メニューとツールバー | Win32 メニューバー + アイコンツールバー | 自前描画のメニューバー(`F9`)。ファイル／表示／ツール／設定／ヘルプに分かれています | 画面全体を自前で描画しており、ネイティブコントロールは使いません。ネイティブメニューはクライアント領域の外にあり文字セルを消費しませんが、自前描画のメニューは必ず 1 行分を消費します |
| ヘルプ | ヘルプファイル | `F1` に内蔵された使用説明 | ファイルを読むのではなく内蔵にしています——インストールディレクトリがない状態、アーカイブの中から実行した状態、Android で読み取れるプログラムディレクトリがない状態、いずれでも呼び出せる必要があるためです |
| プレビューペイン | あり | `Alt-P`、下部 8 行 | テキストは先頭数行、バイナリは 16 進数で並べ、画像はフォーマットとサイズを表示します |
| ステータスバー | 2 行:ファイルフィールド + フルファイル名 | 同じく 2 行、マスごとに突き合わせ済み | 2 行目は原版と**ピクセル単位で同一**です |
| 左側ドライブ列 | Win32 ツールバー横のペイン、ドライブレターを一覧表示 | 一覧左側のセルペイン、`Alt-D` で開閉 | Linux / macOS にはドライブレターがないためマウントポイントを一覧表示します。取り外し可能なものは別の色で表示します |
| スクロールバー | Win32 コントロール | 一番右の列、矢印 + つまみ | 原版のスクロールバーはシステムカラーで描画されており、ピクセル単位の一致は不可能です |
| 半角文字コード表 | CP437 | 同じく CP437 | ANSI art で使う `░▒▓█│─` は 0xB0–0xDF にあり、Latin-1 として扱うとまとめて別の文字として描画されてしまいます |
| 拡張子ごとの配色 | あり(`.bat` は行全体がマゼンタ) | 未実装 | 原版では設定で変更可能でした |
| KK 発音記号 | 独自エンコーディング、1 バイト 1 音素 | IPA 表記に変換して表示(`ˈlɪtl̩`、`ˈbʌtn̩`) | 対応表は `internal/dict/kk.go` に実装 |
| フォントサイズ | 設定で 3 種類のビットマップフォントから選択 | `Ctrl-+` / `Ctrl--` で同じ 3 種類を即座に切り替え | 24 ポイントの全角漢字は倚天のディスクでは圧縮されており、このサイズの中国語は 16×15 を拡大しています |
| ウィンドウ | 固定レイアウト | ウィンドウを大きくすると行列が増える | マスのサイズは変わらず、増えた分だけ表示できる列数・行数が増えます |
| Big5 以外の文字 | Windows のシステムフォントに委ねる | システムフォントディレクトリを走査してフォールバックチェーンを構成 | 簡体字、日本語、韓国語、キリル文字、ギリシャ文字、アラビア文字、タイ文字、数学記号、罫線素片、絵文字まで補えます。本当に無い字は空枠で表示し、空白にはしません |
| マウス | Win32 プログラムなのでもともとクリック可能 | 一覧をクリックでカーソル移動、ダブルクリックで開く、メニューバーをクリックで展開、ホイールでスクロール | 詳細は下の「操作」を参照 |
| 終了して再度起動 | 最初からやり直し | 前回のディレクトリ、カーソル位置、開いていた文書に戻り、**ファイルごとにどこまで見たかも記録** | ディレクトリを切り替えるかファイルを開閉した時点で書き込みます——終了時だけ書き込む方式だと、強制終了やクラッシュで記録が失われるためです |
| 配布方法 | シェアウェア、作者が配布 | BSD 2-Clause(自作部分のみ) | 成果物には原版の半角 `.FON` と倚天の全角字庫を内蔵しており、展開すれば原版に揃った画面になります。これらのフォントの権利は元の権利者にあります。詳細は `NOTICE` を参照。辞書データは同梱していません |

倚天(ETEN、台湾の DOS 時代に使われていた中国語システムです)の行が、
文字の並べ方を決めています。`STDFONT.15` の全角マスはちょうど 16×15 で、
`cvga` 半角 8×15 のちょうど 2 倍の幅・同じ高さです。中国語と英数字が
同じグリッド上に収まり、拡大縮小も余白の補完も必要ありません。

画面の配色は原版を踏襲しています。29 個の named color の名前と RGB 値は
すべて `WINCV.IMG` から解析したもので、新たに配色し直したものでは
ありません。ファイル一覧の各列がどの色を使うかは、両方のスクリーンショットを
同じグリッドで切り分け、マスごとに比較して測定した結果です——インジケーター
列は濃い青一色でカーソルに覆われず、日付は緑固定、時刻はそのファイル自身の
色に従い、ロングファイル名の列には下線が付きます。これらは慣例で推測すれば
すべて外れます。測定結果と再実行の手順は `docs/ui/main-screen.md` に
記載しています。

![F1 メニュー](docs/ui/shot-menu.png)

*`F1` メニューはそのままヘルプでもあります。各行の右側に対応するキーが
表示されており、メニュー内でそのキーを押すと選択したのと同じ動作になります。*

## アーカイブ形式

自前実装した 6 種類のデコーダはすべて参照実装と照らし合わせて 1 ファイル
ずつ sha256 で検証しており、自分自身の出力を期待値として使ってはいません。

| 形式 | 実装 | 検証対象 |
|---|---|---|
| ZIP / TAR / GZ / BZ2 | Go 標準ライブラリ | — |
| RAR / 7z | `nwaples/rardecode`、`bodgit/sevenzip` | 各パッケージ自体 |
| LHA / LZH | 自前実装 | p7zip、675 メンバー |
| `.Z` | 自前実装 | ncompress |
| CAB(MSZIP) | 自前実装 | gcab / cabextract |
| ARJ(方式 0–4) | 自前実装 | arj 3.10 |
| ARC / PAK | 自前実装 | arc 5.21 |
| ACE | 自前実装 | acefile、269 メンバー |

比較対象(oracle)がない形式についてはデコーダを書きません。検証していない
デコーダは、内容があるように見えて実際は誤ったファイルを黙って出力して
しまい、それは「対応していません」と明言するよりもたちが悪いからです。

ACE は原版に内蔵されていません——原版は WinACE 純正の `unace.dll`
(1999 年、v1 API)または `unacev2.dll`(2002 年、v2 API)を読み込んで
いて、`WINCV.IMG` にはバインディング層しかありませんでした。ここでは
Marcel Lemke による 1998 年の〈Technical information of the archiver
ACE v1.2〉に基づいて自前で実装し、BSD ライセンスの
[acefile](https://github.com/droe/acefile) と照らし合わせています。
テストデータには [acefile-testdata](https://github.com/droe/acefile-testdata)
を使用しています。stored、ACE 1.0 の LZ77、ACE 2.0 の blocked(LZ77 /
DELTA / EXE の 3 種類のサブモードを含む)に対応しています。SOUND と PIC
の 2 種類のサブモード、暗号化、マルチボリュームアーカイブは未対応です。

## フォントの置き場所

フォントには由来の異なる 2 つの層があり、探す場所もそれぞれ違います。

**原版のビットマップフォントと倚天字庫**(ピクセル単位で揃っている方)は
サードパーティの著作物です。デスクトップ版のリリースにはこれらを
**実行ファイルに内蔵**しており、展開すればすぐに使えます。Android の
APK には内蔵しておらず、自分でビルドした版にも含まれません。自分で
用意したい場合、あるいは内蔵のものを自分の手持ちのもので上書きしたい
場合は、`cvga.fon`、`CVGA1018.FON`、`cvga1224.FON`、`STDFONT.15`、
`SPCFONT.15` を次のいずれかの場所(先に書かれているものが優先)に
置いてください。シンタックスハイライトの設定 `keyword_*.cfg` と
辞書データも同じ場所を探します。

| 場所 | 説明 |
|---|---|
| `$WINCV_HOME` | 環境変数。ダブルクリック起動やデスクトップショートカットではフラグを渡す場所がなく、そういうときこそ作業ディレクトリが最も予測しづらいタイミングです |
| 実行ファイルのあるディレクトリ | 最も多くの人がこうします。配下の `wincv/`、`original/app/`、`original/eten/` も見ます |
| 個人設定ディレクトリ | Linux は `~/.config/wincv`、macOS は `~/Library/Application Support/wincv`、Windows は `%AppData%\wincv`。`session.json` と同じ慣例です |
| `~/.wincv` | 上記が見つからないときの最後の手段 |
| 作業ディレクトリ | 開発時に repo のルートから実行する場合、素材は `original/` 配下にあります |

Android では外部ストレージの `wincv/` を使い、デスクトップ版の
「実行ファイルの隣の `wincv/`」と同じ名前です。`-half` / `-eten-std` /
`-eten-spc` で直接パスを指定した場合は、常に上記すべてより優先されます。
どこにも見つからない場合、プログラムは探したディレクトリを 1 行ずつ
表示します——「ファイルが見つかりません」というメッセージがどこを
探したか示さないと、ユーザーは推測するしかなく、しかもここはプラット
フォームごとに違う部分だからです。

**Big5 以外の文字**はシステムフォントで補います(簡体字、日本語、韓国語、
キリル文字、ギリシャ文字、アラビア文字、タイ文字、各種記号)。フル
バージョンにはさらに Noto のいくつかのサブセットを内蔵しており、
システムに依存しません。システムフォントの場所はプラットフォームごとに
次を探します。

| プラットフォーム | スキャンするディレクトリ |
|---|---|
| Linux | `/usr/share/fonts`、`/usr/local/share/fonts`、`$XDG_DATA_HOME/fonts`(未設定なら `~/.local/share/fonts`)、`~/.fonts`、`$XDG_DATA_DIRS` 配下の `fonts/`、`/run/host/fonts`(Flatpak)、`/run/current-system/sw/share/X11/fonts`(NixOS) |
| Windows | `%SystemRoot%\Fonts`(`C:\` 固定ではありません——Windows が必ずしも C: にインストールされているとは限らないためです)、`%LOCALAPPDATA%\Microsoft\Windows\Fonts`(Windows 10 の 1803 以降、「自分専用にインストール」したフォントはここに入り、システムディレクトリには表示されません) |
| macOS | `/System/Library/Fonts`、`/System/Library/Fonts/Supplemental`(Catalina 以降付属のフォントがここに移動)、`/Library/Fonts`、`~/Library/Fonts` |
| Android | `/system/fonts`、`/product/fonts`、`/system_ext/fonts`(Android 10 以降、システムは複数のパーティションに分割されています) |

スキャンしたフォントはファイル名でさらに絞り込みます。デスクトップ機の
フォントディレクトリには数百個のファイルがあり、すべて読み込むと数秒
かかり数十 MB を消費します。その大半(装飾フォント、単一言語向けの
飾り文字)は、どの欠字も補えません。認識する名前は 4 プラットフォーム
それぞれの内蔵フォントを網羅しており、Noto だけではありません——
Noto しか認識しなければ、Windows と macOS ではスキャンしても 1 つも
見つからず、それではスキャンする意味がなくなってしまいます。

## リメイク版で追加した機能

原版になく、この版にはあるもの:

| 機能 | 説明 |
|---|---|
| markdown 表示 | `.md` を開くとそのまま整形されます:見出し、リスト、テーブル、引用、コードブロック。**画像は文書内に埋め込んで表示**(PNG / GIF / SVG に対応)、`Enter` で画像を拡大 |
| SVG | パスは oksvg でラスタライズし、テキストは自前で描画します(oksvg は `<text>` に対応していないため)。原版は 2011 年のソフトウェアで、当時 SVG はまだ普及していませんでした |
| UTF-8 フォールバックフォント | 倚天にない文字はシステムの TrueType で補い、決め打ちのパスだけでなくフォントディレクトリを走査します |
| フォントサイズと倍率 | `Ctrl-+`/`Ctrl--` でビットマップフォントのサイズを切り替え、`Alt-+`/`Alt--` で倍率を拡大(1 回につき 0.1)。倍率はグリフを単純に引き伸ばすものではありません。原版に付属する 3 種類のビットマップフォント(8×15 / 10×18 / 12×24)の間の比率はちょうど 1.19 と 1.56 なので、1.2 / 1.5 / 1.6 のあたりでは**ネイティブのグリフ**に切り替わり、各ピクセルが当時デザインされたものになります |
| ウィンドウサイズ | `F9` → 設定 → ウィンドウサイズ。原版のレイアウトである 93×21 などのプリセットがあり、列数・行数を自分で指定することもできます |
| ネットブラウジング | `F2` でアドレスを入力。`gopher://` と `http(s)://` は**同じ画面、同じキー操作**で扱えます:`↑↓` でリンクを移動、`Enter` で開く、`Backspace` で前のページへ。ウェブページはテキスト、リンク、画像だけを残し、スタイルシートとスクリプトはすべて捨てます |
| 電子書籍 | `.epub` は `Enter` でまず目次を表示し、章をクリックして読み進めます。章の末尾には前後の章への移動があります。EPUB は ZIP + XHTML なので、両方の部品はもともと揃っています |
| PDF | 2 通りの見方があります。`Enter` で 1 ページ目の**テキスト**を開く(文字を行として組み直し、段組を検出)、`V` でページ全体を**描画**する(拡大可能、下記参照)。詳細は次の節を参照 |
| テキスト表示のカーソルバー | `.txt` を読んでいるとき、カーソルのある行全体をハイライトします。`↑↓` でカーソルを移動し、画面外に出るとスクロールします。原版のツールバーは常にカーソルが何行目にあるかを表示していましたが、その行自体は描画していませんでした。デフォルトで有効、`L` で無効化(ANSI カラーの署名ファイルは背景色自体に意味があるため) |
| Word | `.docx`、`.doc`(Word 97–2003)、`.rtf` の 3 種類に対応:見出し、太字・斜体、番号付き・箇条書きリスト、テーブル、埋め込み画像 |
| PowerPoint | `.pptx` はスライド 1 枚を 1 段落として扱い、スピーカーノートも一緒に収録します。先頭にスライド一覧があります |
| Excel | `.xlsx` はシート 1 枚を 1 段落として扱い、セルはテーブルとして並べます |
| 多言語対応 | インターフェースは繁體中文・简体中文・English・日本語に対応しています。起動時にシステムのロケールを見て、`F9` → 設定 → 言語 でいつでも切り替えられ、選んだ言語は記憶されます。`F1` の使用説明も言語ごとに用意されています |
| メニューフォントの分離 | メニュー層には独自のグリッドがあり、コンテンツとは**異なるフォントとサイズ**を使えます(`F9` → 設定 → メニューフォントサイズ、または起動時に `-menu-font`)。コンテンツは原版とピクセル単位で揃える必要がありますが、メニューはあくまでインターフェースです |
| ファイルごとの表示位置の記憶 | テキスト、HEX、markdown、エディタはいずれも、離れてから戻ると前回の位置に戻ります(エディタはカーソルの行と列まで記憶)。ファイルごとに 1 件、最大 500 件まで。原版の 0.5x にもこの設定はあり、リメイク版でもデフォルトで有効です |
| メインファイル名列の幅調整 | 原版の一覧は常に 8.3 形式のレイアウトで、長いファイル名は一番右の列に送られます。この版ではメインファイル名列を広げることができ(`Ctrl-→` / `Ctrl-←`、または一覧上で左ボタンを押しながら横にドラッグ)、長いファイル名を一覧内にそのまま表示できます。幅は記憶されます |
| 画像と PDF 全体表示の拡大 | `+` / `-` で段階的に拡大縮小、`1` で元のサイズに戻ります。PDF の全体表示は**より高い解像度で再描画**するもので、ビットマップを引き伸ばすのではありません——拡大するとテーブルの細い罫線や小さな脚注の文字まで見えます |

![テキスト表示のカーソルバー](docs/ui/shot-viewer-bar.png)

*テキストファイルを読んでいるとき、カーソルのある行全体をハイライトし、
ステータスバー右側に `15/626` のように表示されます。原版のツールバーは
常にカーソルが何行目にあるかを表示していました(「1 字 1 行/ 626」)が、
その行自体は描画していませんでした——長いファイルを途中までスクロール
したとき、「さっきどこを見ていたか」は 1 本の線で記憶されていたのです。
ANSI カラーの署名ファイルは背景色自体に意味があり、上書きすると情報が
失われるため、`L` で無効化できます。*

![gopher メニュー](docs/ui/gopher-menu.png)

*gopher メニュー。タイプを表すラベルが各行の先頭に付き、インフォメー
ション行にはラベルもリンクもありません。*

HTTP ではなく gopher を選んだのは、プロトコルの形が理由です。1 行に
1 項目、タイプは先頭 1 バイトで表され、メニューの構造はほぼディレクトリ
一覧そのものです——それはまさにこの画面がやっていることです。HTTP の
難しさはすべて HTML にあり、HTML が要求するレイアウト、フォント、
スクリプトは、この画面には 1 つも提供できません。テキストの内容は
**改行し直しません**(gopher のコンテンツの多くは 70 カラムで整形済みの
ASCII です)。エンコーディングは既存の判定器に任せます(gopher には
charset フィールドがなく、あの時代の中国語サイトの多くは Big5 でした)。

markdown 内の画像は**文書のあるディレクトリ配下**の相対パスのみを認識し、
リモート画像はダウンロードしません——文書を 1 つ見ることが外部への通信に
なってはならず、また出所のわからない `.md` が別の場所のファイルを読める
ようになってもいけないためです。

## 操作

キー操作は原版を踏襲しています(キーごとに実測した対応表は
[`docs/ui/keymap.md`](docs/ui/keymap.md))。リメイク版ではさらにマウス
操作と、原版にはいくつかの動作を追加しています。

| メイン画面 | |
|---|---|
| `↑` `↓` `PgUp` `PgDn` `Home` `End` | カーソル移動(**長押しで自動リピート**) |
| `Enter` | ディレクトリに入る／ファイルを開く。アーカイブも `Enter` で中に入ります |
| `Space` | マーク。`C` でコピー、`M` で移動、`R` でリネーム |
| `Ctrl-→` / `Ctrl-←` | メインファイル名列を 1 マス分広げる／狭める |
| `F1` `F2` `F9` | 使用説明／ネットブラウジング／メニュー |
| `Ctrl-+` `Ctrl--` ／ `Alt-+` `Alt--` | フォントサイズ／拡大倍率 |
| `Alt-D` `Alt-P` | ドライブペイン／プレビューペイン |

| マウス | |
|---|---|
| 一覧を単クリック | カーソルがそこに移動 |
| 一覧をダブルクリック | `Enter` と同じ:ディレクトリに入る、ファイルを開く |
| メニューバーを単クリック | そのカテゴリを展開。もう一度クリックすると閉じる。コンテンツ領域をクリックした場合はメニューを閉じるだけで、その下の操作は行いません |
| 一覧を横にドラッグ | メインファイル名列を広げる／狭める |
| ホイール | 1 段 = `↑`／`↓` 3 回分。各モードでの意味はそれぞれのキーに準じます |
| ウェブページ上のリンク | 単クリックで移動します(ブラウザの操作感に合わせ、ダブルクリックは要求しません) |

方向キーを押しっぱなしにしたときの自動リピートは自前で実装する必要が
ありました。Ebiten は「押した瞬間」しか通知せず、OS 側のキーボード
リピートはそこを通らないためです——実装しなければ `↓` を押しっぱなしに
しても 1 マスしか動かず、1 つのディレクトリには数百個のファイルが
入り得ます。

## Office 文書と PDF

原版にはこれらの形式が存在しないため、原版を対照にはできません——対照
するのは外部ツールです。Office 系統はコンテナ内の LibreOffice に同じ
ファイルをプレーンテキストへ変換させ、PDF のページ全体描画は poppler と
照らし合わせます。以下のスクリーンショットで使っているサンプル文書は
[`docs/demo/office/`](docs/demo/office/) にあり、内容は本プロジェクトが
独自に作成したものです。再構築と再撮影の手順は同ディレクトリの README に
記載しています。

5 種類の Office 形式は同じ狭いインターフェース(`internal/officedoc`)の
背後に収めています。このインターフェース層は「いくつかの段落 ＋ いくつかの
画像」しか認識しないため、6 番目の形式を追加してもこの層は 1 行も変更する
必要がありません。

### Word

![Word 文書](docs/ui/shot-docx.png)

*`.docx` を開いた様子:見出し、太字、番号付きリスト、テーブルがすべて
同じ文字セルグリッドに整形されます。`.doc`(Word 97–2003 の FIB ＋
piece table)と `.rtf` も同じ画面を通ります。*

### PowerPoint

![PowerPoint プレゼンテーション](docs/ui/shot-pptx.png)

*`.pptx` はスライド 1 枚を 1 段落として扱い、スピーカーノートはその
スライドの後に続けて収録されます。下部の「スライド一覧 ／ 次の
スライド」は EPUB の章ナビゲーションと同じ仕組みです。*

### Excel

![Excel スプレッドシート](docs/ui/shot-xlsx.png)

*`.xlsx` のセルはテーブルとして並びます。共有文字列テーブル、数値の
書式、日付シリアル値はすべて解析層で変換済みで、画面側にはテキストしか
見えません。*

### PDF:2 通りの見方

PDF が記述しているのは「この文字をこの座標に置く」ということだけで、
段落もカラムも読み順もありません——それらはレイアウトの結果であって、
データそのものではないのです。そのためテキスト抽出のルートでは、
文字を自前で行に組み直し、さらに段組を検出しています(判定基準は
「ページ上端からページ下端まで通っていて、どの文字もまたがない縦方向の
空白帯」で、さらに「各カラムの大半の行がカラム幅をほぼ埋めているか
どうか」でテーブルを除外しています)。

| テキスト抽出(`Enter`) | ページ全体描画(`V`) |
|---|---|
| ![PDF テキスト抽出](docs/ui/shot-pdf-text.png) | ![PDF ページ全体](docs/ui/shot-pdf-page.png) |

左側は文字を探すのが速く、右側はテーブル、図表、数式、署名といった
「位置に意味がある」ものまで見えます。

ページ全体描画は自前で書いたレンダラーで、新たな依存関係は追加して
いません——ラスタライザーは SVG のルートで既に使っている `rasterx` を、
グリフ輪郭は `x/image/font/sfnt` に自前実装の CFF・Type1 インタープリタを
組み合わせています。

| | |
|---|---|
| パス | 塗り・線、線端、接合、破線。non-zero winding と even-odd の両方の塗りつぶし規則 |
| 色 | Gray / RGB / CMYK / ICCBased / Indexed / Separation |
| 画像 | オブジェクト層で扱えないものは自前でデコード:DCTDecode はそのまま JPEG として扱い、それ以外は生のサンプル値をたどり、画像自身の `/SMask` も適用します |
| グラデーション | 軸方向・放射方向。指数関数、結合、サンプリングの 3 種類の関数。グラデーションを塗りつぶしパターンとして使用 |
| 透明度 | 定数透明度、輝度と alpha の 2 種類のソフトマスク、透明グループ |
| フォント | TrueType/OpenType、CFF、Type1 の 3 種類の埋め込み形式すべてで輪郭を解釈し、`seac` によるアクセント合成にも対応 |

検証の対照は poppler、もう 1 つの独立した PDF レンダラーです。手書きの
最小サンプル(グラデーション、透明度、アクセント合成、画像)ではインク
密度の相関係数がいずれも 0.9997 以上でした。実際の論文、カタログ、
スライドで測定した 6 ページでは、すべて 0.95 以上でした。

どの機能を実装するかは実測で決めており、仕様書のチェックリストを
なぞったものではありません。`tools/pdfprobe scan` で実際の PDF 105 件を
スキャンしたところ、タイリングパターン、メッシュグラデーション、
PostScript 計算関数は**1 件も現れませんでした**。この 3 項目は非対応と
明言しています——理解できないグラデーションは白紙のままにし、推測した
色を塗りつぶしたりはしません。測定方法と数値は
[`docs/plan/office-docs.md`](docs/plan/office-docs.md) にあります。

`DroidSansMono.ttf`」というメッセージ行です——APK には原版の
`cvga.fon`(サードパーティの著作物)を含めていないため、ユーザーが
`wincv/` に自分で配置して初めてピクセル単位で揃ったビットマップ版に
切り替わります。

`tools/build-android.sh` が APK をビルドし(4 つの ABI、minSdk 21)、
`tools/run-android-emulator.sh` がそれをエミュレータにインストールして
起動し、スクリーンショットと logcat を取得します。**まだ実機では動かして
おらず、タッチ入力もまだ実測していません**——スクリーンショットは画面が
描画できファイルが読めることを証明しますが、タップして反応することまでは
証明していません。

下部は 3 行構成です。一番上の行の動作はモードによって変わります
(ブラウジング中はマーク／コピー／移動／リネーム、文書表示中は検索／
エンコーディング／中英切り替え、画像表示と PDF ページ全体表示では
前へ／次へ／縮小／拡大／原寸)。下の 2 行は固定のキー HUD です——

```
Esc  | PgUp | ▲ | PgDn | Enter
Home | ◀    | ▼ | ▶    | End
```

方向キーは十字に並び、`Esc` と `Enter` は異なる色で両端に配置されて
います。HUD には**実在するキーだけ**を置いているため、「このモードでは
押しても反応しないボタン」が現れることはありません。モード固有の動作は
上の行にあります。

実物のキーボード(ドック、Bluetooth)を接続した場合、キー操作はデスク
トップ版と同じです——キーボード変換の実装は 1 つだけ(`internal/ebikeys`)
で、Ebiten は Android 上でも `KeyEvent` を同じ `ebiten.Key` として送って
きます。この経路はコンパイルの確認のみで、**実機でキーボードを接続した
実測はまだありません**。

Android への移植で実際に時間がかかったのは `internal/` 配下のパッケージ
(こちらは 1 行も変更せずビルドが通りました)ではなく、Ebiten の Android
層に隠れていた 3 つの挙動でした。gomobile のネイティブ層には自分で
`Context` を渡す必要があること、Activity が一度再生成されると app が
終了したのと同じ扱いになること、`Layout` は受け取ったサイズをそのまま
返してはいけないことです。この 3 点の原因と症状は
[`docs/plan/android.md`](docs/plan/android.md) にまとめています。
